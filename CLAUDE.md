# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Hugo static site for `lna-dev.net` (personal site of Lukas Nagel). Theme is `hugo-PaperMod`, pulled in as a Hugo Module via `go.mod` (no submodules). Trilingual: English (default), German, Swedish — each language gets its own subdirectory in URLs (`defaultContentLanguageInSubdir: true`).

## Build / Deploy

- Local build: `hugo` — output goes to `public/`.
- Local server: `hugo server -D` (drafts on).
- Deploy: `./deploy.sh` builds twice (clearnet + Tor onion `baseURL`) and rsyncs `public/` to the production server. **Do not run this without the user's say-so** — it pushes live. Each build is followed by `scripts/gallery-embed-metadata.py` and its `--check` before the rsync — see *Embedded metadata in the served files* below. That adds ~3m40s per build (~7m30s per deploy).
- Module bootstrap (only if `go.sum` is missing/broken): `go mod download`.
- Image binaries are intentionally **not in git** and live outside the repo. Hugo mounts them in via `module.mounts`, mapping the local photo store to the `assets/images/gallery/` virtual path. Because that source is an **absolute, machine-specific path**, the mount lives in the gitignored **`config/_default/module.yaml`**, not in `hugo.yaml`. Per machine, set it up once: `cp config/_default/module.yaml.example config/_default/module.yaml` and put that machine's photo-store path in the gallery `source`. A clean checkout without it builds fine but renders an empty gallery (`gallery-images.html` warns when the mount is empty). Two things to know:
  - **`mounts` is replace-not-merge.** A `module.mounts` list in `config/_default/module.yaml` silently discards the whole list in `hugo.yaml` — which is why the local file restates the default `assets` mount and why `hugo.yaml` deliberately declares no mounts at all. Everything else in `hugo.yaml` is still read normally.
  - **A symlink can no longer be the mount `source`.** It used to work — that is what the old repo-root `gallery-photos` symlink relied on — but only because of a Hugo regression (`RootMappingFs.statRoot` calling `Stat` instead of `Lstat`, introduced in 0.123.0). That was a symlink-confinement bypass (CVE-2026-58403) and was fixed in 0.163.1, so from Hugo 0.163.1 on a symlinked mount source resolves to nothing — no error, just an empty gallery. Do not reintroduce one. See memory `project_gallery_mount.md`.

## Architecture

### Gallery system (the load-bearing part of the site)

The gallery was recently restructured (see memory `project_gallery_overhaul.md`). The model is **one flat image folder + central YAML metadata + theme dispatch**. Understanding this is essential before touching any gallery template.

- **Image source of truth**: the local photo store, mounted to the `assets/images/gallery/` virtual path (via `module.mounts` in `config/_default/module.yaml` — see Build / Deploy). All photos sit flat there as global resources regardless of which view they appear in; templates address them as `images/gallery/*`, unaffected by where the files physically live.
- **Metadata source of truth**: `data/gallery.yaml` — one entry per image with `id` (UUID, stable across renames), `src` (current filename), `category`, `section` (`general` | `archive`), `project` (slug, list of slugs, or empty — a photo may sit in several albums, e.g. a thematic one and a single-session one), `portfolio` (bool), `species`, `tags`, `alt`, `title`, `description`, `license`, `artist`. The `src` field must exactly match the image filename. The `id` is the **stable identifier** used by deep links, the likes API, and `featured_image:` references — when a filename changes, only `src` is updated; `id` stays. Three of those fields have a shape worth knowing:
  - **`title`, `alt`, `description` are per-language.** Each is either a bare string (which means English) or an `{en, de, sv}` map, and every read falls back to `en` — the same rule the dex applies to species prose. `gallery-meta.html` normalises the string form into a map so a template only ever meets one shape; `collect-images.html` does the language pick. **`alt` and `description` are different things**: `alt` is the short account of what is visible that goes on the `<img>`, `description` is the prose the photo page prints, and `description` falls back to `alt` when absent.
  - **`license` is a key into `data/licenseMap.yaml`** (`cc-by-sa-4.0`, `all-rights-reserved`), not a display string. The English display strings the entries used to hold were rewritten to keys by the one-time import (`docs/concepts/gallery-metadata-import.md`, **done**), and the `aliases` lists that resolved them went with it — a `license:` that is not a key is now a build error. The map holds `url`, optional per-language `url_by_lang` (CC's translated deeds), a `label` and the `terms` sentence embedded into the served files.
  - **`tags` is deliberately NOT the only source.** Tags are typed in darktable and read live out of the file's `dc:subject` at build time; `tags:` in the YAML is an optional addition and the site shows the union. Junk the camera and the export chain write into that list (`zsl_sdr`, frame-grab clip paths) is dropped via `data/galleryTagIgnore.yaml` at the one place the union is formed. Tags are the **only** thing the build still reads out of a file: the EXIF `alt`, `license` and `artist` fallbacks left `collect-images.html` with the one-time import, so everything else editorial comes from the YAML alone and a darktable re-export can no longer change what the site says about a photo.
- **Two cached partials underpin everything else**:
  - `layouts/partials/gallery-images.html` — returns all gallery image resources via `resources.Match "images/gallery/*"`. Global resources are inherently language-independent. Always call via `partialCached`. Note: `.Name` on these resources returns a full path with a **leading slash** (`/images/gallery/photo.jpg`) — use `path.Base` when looking up by bare filename. Match patterns are matched with or without the leading slash, so `resources.Match "images/gallery/*"` is unaffected.
  - `layouts/partials/gallery-meta.html` — returns `{ bySrc, byId }`, two dicts sharing the same metadata entries. `bySrc` is keyed by bare filename (use `path.Base` on resource `.Name` to match); `byId` is for UUID lookups (`featured_image`, etc.). Each entry gains a derived **`.projects`** key — `project:` normalised to a slice — and that is the only field any template should read for album membership (`in $meta.projects $slug`); comparing `.project` directly breaks the list form, and `in` on the raw string would match a substring (`eagles` against `eagles-2026`). It also normalises `title`, `alt` and `description` **in place** from string-or-map to an `{en, de, sv}` map — never print one of those three straight off an entry, you would get a Go map literal. Nothing is *resolved* here on purpose: `head.html` calls this partial through `partialCached` with **no language key**, which is correct only while the return value stays language-neutral. Hard-fails the build if any entry lacks an `id` — run `scripts/add-gallery-ids.py` to populate one. Always call via `partialCached`.
- **`layouts/partials/collect-images.html`** is the single entry point for collecting+filtering images. It merges the YAML's editorial fields with the file's technical EXIF/XMP, picks `.Title` / `.Alt` / `.Description` for `site.Language.Lang` with an English fallback, resolves the license through `layouts/partials/license-index.html` (a missing `license:`, or one that is not a key, is a hard error naming the photo) and the artist (data → `site.Params.author.name`), and filters the tag union through `data/galleryTagIgnore.yaml`. Filter keys: `category`, `section`, `portfolio`, `project`, `species`, `id`, `excludeArchive` (default true). Each returned item exposes `.Id` (UUID from YAML) — use it as the stable identifier in any new template — plus `.LicenseKey` / `.LicenseText` (the resolved label) / `.LicenseUrl` / `.LicenseTerms`. It is **not** `partialCached` at its call sites and runs once per dex species page, so the per-photo work in it is hot: the language pick and the tag blacklist are inlined rather than delegated to a partial for that reason. It also exposes `.Software` from EXIF (the editing program and version, e.g. `darktable 5.0.1`), with a filter that drops bare version strings: cameras write their own **firmware** version into the same EXIF tag, and 157 of the 633 photos say only `Ver.1.2`, which is not editing software. Use this — do not iterate the bundle directly.
- **`layouts/partials/resolve-featured-image.html`** resolves a `featured_image:` front-matter value (UUID, with legacy filename fallback) to a bundle resource. Used by `get-gallery.html` and `templates/_funcs/get-page-images.html`.
- **Theme dispatch**: gallery pages select a renderer through their front-matter `params.theme`, branched in `layouts/_default/list.html` and `layouts/_default/single.html`. Themes:
  - `gallery-home` → `content/gallery/_index.*` — hero portfolio + nav cards to Projects/General + Archive link.
  - `gallery-general-home` → `content/gallery/general/_index.*` — all non-archive images with category filter bubbles (`gallery-filter-bubbles.html`, JS-only client-side filtering on `data-category`).
  - `gallery-archive` → archive view (forces `section=archive` filter).
  - `gallery-portfolio` → curated subset (`portfolio: true`).
  - `gallery-projects-list` → index of project mini-albums.
  - `gallery-project` → single project album (filters by `project_slug`). An album is kept **out of the projects index** with Hugo build options in its front matter — `build: {list: never, render: always}` (the key is `build`, not the removed `_build`), which also drops it from the sitemap and the section RSS while still rendering it at its URL; pair it with `params.robotsNoIndex: true` for an unlisted album. Note this hides the *album*, not its photos — `/gallery/general/` shows every non-archive photo whatever its project.
  - `gallery-page` / `gallery-page-hidden` → generic gallery single pages.
- **Lightbox**: PhotoSwipe, wired up in `assets/js/lightbox.js`; thumbnail and full-size images are generated by Hugo image processing in `gallery.html` (600px and 4000px fits).

### Embedded metadata in the served files

Hugo cannot write image metadata. It re-encodes every variant and emits no metadata segment at all, so for a long time a visitor who downloaded a photo got a JPEG with no licence, no creator and no title — while the untouched original was published alongside it (the microdata `contentUrl` references `$image.Permalink`, and referencing a resource publishes it) carrying camera serial numbers, GPS on the drone shots, darktable ratings and an embedded EXIF thumbnail that can show the uncropped frame. `scripts/gallery-embed-metadata.py` inverts that, as a post-build pass over `public/`:

```
hugo  →  scripts/gallery-embed-metadata.py  →  --check  →  rsync      (deploy.sh does this twice)
```

- **Source originals are never written to.** The photo store is darktable's export target and a Nextcloud folder. Only build output is touched — every file under `public/images/gallery/`, the published copy of the original included.
- **It resolves nothing itself.** Hugo writes the resolved values to `public/<lang>/gallery-metadata.json` (the `gallerymeta` output format in `hugo.yaml` + `layouts/_default/home.gallerymeta.json`, rendered from `gallery-collected.html`); the script merges the three on `id` and writes them out. A Python re-implementation of the string-or-map language fallbacks, the licence map and the tag union would be a second resolver to keep in step with `collect-images.html`. **Unlike `securitytxt`, `gallerymeta` is in the top-level `outputs.home`** — every language must write its own copy — which also means it has to be restated in `languages.en.outputs.home`, since a per-language `outputs` replaces the top-level list rather than extending it.
- **The technical half is copied, not stored.** `-tagsFromFile <source>` pulls camera, lens, exposure, date and software straight out of the original in the same exiftool call. **Never `Orientation`** — `AutoOrient` bakes the rotation into a variant's pixels, so copying the tag would rotate it a second time in any viewer that honours it.
- What is written: `dc:creator`/`Artist`/`By-line`, a real copyright **notice** (`© <capture year> <artist>`, not the licence name — and with **no year** on the 92 photos whose capture year is unknown, since the build year would both assert a wrong year and rewrite those files every New Year's Day), `xmpRights:UsageTerms` with `xml:lang` alternatives, `WebStatement` + `plus:LicensorURL` (the two IPTC fields Google reads for the *Licensable* badge), `photoshop:Credit`, `DigitalImageGUID` = the photo's UUID, `dc:title`/`dc:description` per language, and the filtered tag list. Every XMP field gets its IPTC-IIM spelling beside it, clipped to the IIM length limits, because older software reads only IIM. URLs are always clearnet, in the Tor build too — an onion address inside a JPEG is not a useful licensor contact.
- What is stripped: serial numbers, `MakerNotes`, `GPS*`, `IFD1` (the thumbnail), ratings and colour labels, `XMP-darktable`, `XMP-acdsee`. **The ICC profile is left alone** — colour depends on it — but a *variant* gets an explicit `ColorSpace=sRGB`, because Hugo drops the profile and exiftool would otherwise fill the mandatory tag of the EXIF block it creates with "Uncalibrated", telling a colour-managed viewer the pixels are not sRGB when they are.
- **`--check` reads every served file back** and asserts `DigitalImageGUID` matches the manifest. `deploy.sh` runs it before each rsync, so nothing ships untagged. A published file that maps to no manifest record aborts the run before anything is written.
- Cost: ~3m40s for 4,161 files / 7.6 GB, and **deterministic** — a second run leaves every file byte-identical, so the pass is idempotent and rsync transfers nothing extra for it.
- Tagging `resources/_gen/images/` instead would make the cost one-off, and is the documented escape hatch if the per-deploy time ever bites. It is not the default: the cache is an intermediate, it is the one thing in this repo that must not be corrupted (a cold rebuild runs past ten minutes), and "outputs yes, sources no" is a cleaner line.

Full design, including what is deliberately out of scope: `docs/concepts/gallery-metadata-single-source.md`.

### Inlining a gallery photo in a post

`layouts/shortcodes/galleryImage.html` puts one gallery photo into a post body, addressed by its **UUID** from `data/gallery.yaml` (`{{< galleryImage id="…" >}}`) — the id rather than the filename, so a rename in the photo store does not break the post. It resolves the photo through `collect-images.html` (new `id` filter key; pass `excludeArchive false` with it, as the shortcode does, since naming a photo by hand is explicit), so an inlined photo carries exactly the metadata the gallery shows. An unknown id is a **hard build error** with file:line, not a silent blank.

Rendering is one fixed path: `AutoOrient`, then width-constrained `fit` variants at 480/720/1080/1440 px — capped at the original width so a small file is never upscaled — with `src` pointing at the 720 px variant (`--main-width`), `sizes="(max-width: 720px) 100vw, 720px"`, and `width`/`height` set against layout shift. The height bound in the `fit` spec is deliberately 10× the width so tall portraits stay full-width instead of being shrunk to a square, unlike the gallery grid's `fit 600x600`.

Both caption lines are **off by default** (`showTitle`, `showExif`; `caption="…"` overrides). `alt` and `title` come from `data/gallery.yaml` resolved into the post's language, so a German or Swedish post only needs `alt="…"` / `caption="…"` where that photo has no translation yet or the post wants different wording. The default link is a deep link to `/gallery/general/#<uuid>` (or `/gallery/archive/` for archived photos) resolved via `site.GetPage`, which is language-correct and survives the gallery moving; `lightbox.js` matches `window.location.hash` against the `data-id` there and opens PhotoSwipe. `link="false"` renders no link. There is **no per-category gallery page** — `/gallery/general/` holds every non-archive photo. SEO markup mirrors `gallery.html`: schema.org `ImageObject` microdata with license, creator, credit and copyright. Styles are `assets/css/extended/galleryImage.css`.

`layouts/shortcodes/galleryImageText.html` is the paired variant: a photo beside its text, in a block that breaks out of the 720px column to `--nav-width` (1060px here — `assets/css/extended/navbar.css` overrides PaperMod's 1024 default). It exists because a 45% photo *inside* 720px leaves a ~372px text column (~41 characters), which the theme's `word-break: break-word` then splits German compounds across; at the header width it measures 466px photo / 570px text, ~63 characters. Centring uses `margin-left: 50%` + `translateX(-50%)`, and the width is capped at `100vw - 2*gap` rather than `100vw` because the latter includes the scrollbar. It stacks below **900px**, not the theme's 768px breakpoint — at 768px the text track is back to ~44 characters — and the photo always comes first when stacked, whichever `align` it has on desktop. `galleryImage` also takes `align="left|right"`, which floats the photo so **ordinary Markdown paragraphs wrap around it** — no moving prose into a shortcode, which is the usual case for a photo essay and the reason `galleryImageText` is the exception rather than the default. The float is pulled into the margin between `--main-width` and `--nav-width` (170px per side): a 340px photo then eats only 170px of the text column, leaving ~58 characters instead of the ~41 an in-column float would. The negative margin is clamped to `min(170px, (100vw - main - 2*gap) / 2)` — below ~1108px viewport that margin does not exist yet, and a fixed -170px would push the photo off-screen. Headings do **not** clear the float — a heading sets beside a photo exactly as a paragraph does, so a whole section can run alongside a tall portrait. (They used to carry `clear: both`; that left ~270px of dead space whenever the wrapping text was shorter than the photo, and letting the next section flow into it is the only way to fill it. PaperMod gives headings no border or background, so a shortened heading line shows no seam.) Full-width `figure`s do still clear — see `assets/css/extended/img-shortcode.css` — because a figure's `<img>` is 100% of the figure width and would run straight through the float instead of wrapping. `size` tunes the width per call — `small` (280px) / `medium` (340px, default) / `large` (420px), or a bare pixel number — and works without `align` too, where it caps and centres an otherwise full-width photo. The resolved pixel value drives **both** the CSS `--img-width` and the `sizes` attribute from one place, so a smaller photo actually downloads a smaller file instead of being scaled down in CSS; an unknown value is a hard build error.

Both shortcodes share `layouts/partials/gallery-image-figure.html`; the only things that differ are the CSS class and `sizes`.

### Activity feed

`content/feed/_index.*` + `layouts/feed/list.html` builds a unified activity timeline by merging:
1. All `RegularPages` in the `posts` section across all languages (`lang.Merge`),
2. Photos from the gallery headless bundle (filtered to non-archive, dated >2000),

### Reading list

Books the user has read. **Data**: `data/reading.yaml` — a flat list, one entry per book. Fields: `title`, `series` (optional), `author`, `genres[]`, `year`, `link`, `cover`, `pages`, `originalLanguage` (2-letter code), `languagesRead[]` / `languagesListened[]`, and optional `rating` (1–5), `dateRead` (`"YYYY-MM-DD"`, drives the `recentReading` preview order), `notes`. **Covers**: committed JPEG/WebP files in `assets/images/books/covers/`, referenced as `images/books/covers/<Title>.<ext>` and resized to a 200×300 fit by Hugo. Unlike gallery photos, these images *are* in git. Rendered by `layouts/shortcodes/readingList.html` (full list) and `layouts/shortcodes/recentReading.html` (profile-page preview).

**Adding a book — use `scripts/add-book.py`** (stdlib only; see `AGENTS.md` for the full workflow). It looks the book up on Open Library (free, no key), downloads the cover into the covers folder, and appends a YAML entry (`--append`) or prints a paste-ready block. It auto-fills `title`/`author`/`year`/`pages`/`cover`, proposes a `link` (Wikipedia → Open Library → Goodreads-search, always verify), and suggests `genres` mapped onto the existing vocabulary. It **cannot** know `originalLanguage`, `rating`, `dateRead`, `languagesRead`/`languagesListened` — those are left as TODO/empty for a human. Always eyeball the link and genres before committing (subject mapping produces occasional false positives). Do **not** run `./deploy.sh` after adding — that is a separate, explicitly-authorized step.

### Gaming

Games the user has played, modelled on the reading list. **Data**: `data/gaming.yaml` — a flat, unordered list, one entry per game, written by **multiple sources**. The `platform` field is the discriminator (`steam` | `epic` | `gog` | `switch` | `playstation` | `manual` | …). Fields: `title`, `platform` (both required), `appid` (Steam only — the **stable key** the Steam sync matches on) / `appName` (Epic + GOG — the stable key those syncs match on; for GOG it's the numeric product id), `playtimeMinutes`, `lastPlayed` (`"YYYY-MM-DD"`), `achievementsUnlocked` / `achievementsTotal`, `cover`, `link`, and the optional human-owned `rating` (1–5), `genres[]` / `tags[]`, `notes`, `extraMinutes` (hand-entered untracked/estimated minutes, **added to `playtimeMinutes`** in every UI total — folded in at the `gaming-merged.html` sum). **Covers**: committed JPEGs in `assets/images/games/covers/` named after the game title (`<Title>.jpg`, like book covers — `scripts/sync-steam.py` writes them that way), referenced as `images/games/covers/<file>` — in git, unlike gallery photos. **Rendered by** `layouts/shortcodes/gamingList.html` — a Steam-library-style cover grid at `/gaming/` with a stats header (game count, total hours, achievements), client-side sort (playtime / recently-played / A–Z), and a platform-filter row shown only when ≥2 distinct platforms are present — plus `layouts/shortcodes/recentGaming.html`, a recently-played preview row on the About page mirroring `recentReading`. Content pages are `content/gaming/index.{en,de,sv}.md` (leaf bundles whose body is just `{{< gamingList >}}` — no `theme` dispatch); styles are `assets/css/extended/gamingList.css` + `recentGaming.css` (auto-bundled, theme-variable-based so they work in light/dark); i18n lives under the `# Gaming` block in `i18n/{en,de,sv}.yaml`. Covers are resolved with `resources.Get .cover` + `.Fill "300x450"` for uniform tiles, with a title placeholder when a `cover` is absent. Not in the nav menu (reached via the About preview + the `/gaming/` URL), matching the reading list. **Hiding a game**: add its exact `title` to the `titles:` list in `data/gamingIgnore.yaml` (case-insensitive, whitespace-trimmed) — the entry stays in `data/gaming.yaml` and keeps syncing, but is dropped from every view. The filter lives at the shared choke point `layouts/partials/gaming-merged.html` (used by both `gamingList` and `recentGaming`), so it applies to the grid, the stats header, and the About-page recent row alike.

**Syncing Steam — use `scripts/sync-steam.py`** (stdlib only; see `AGENTS.md` for the full workflow). It owns only the `platform: steam` entries: it fetches the owned-games library from the Steam Web API, optionally per-game achievements + portrait covers, and **rebuilds** those entries (new games added, de-listed games pruned) as the last block in the file, below a marker it emits. Everything that is **not** `platform: steam` is left byte-for-byte untouched (raw-text editing, no YAML dep), so hand-added games are safe. Human-owned fields (`rating`/`genres`/`tags`/`notes`/`extraMinutes`) on a Steam entry are preserved across syncs — re-emitted verbatim, keyed by `appid` (keep them single-line). Needs `STEAM_API_KEY` + `STEAM_ID` (env or flags; never commit them). Default excludes 0-playtime games (`--include-unplayed` to keep them). Do **not** run `./deploy.sh` after syncing — separate, explicitly-authorized step.

**Syncing Epic — use `scripts/sync-epic.py`** (stdlib only; see `AGENTS.md`). Epic has **no** Steam-style public API, so this merges **two disjoint sources**, both already on disk from the **Heroic** launcher (no separate login): the owned library + Heroic-launched playtime (`store_cache/legendary_library.json` + `store/timestamp.json` under the Heroic config), and — by reusing the Epic OAuth refresh token Heroic stored (`legendaryConfig/legendary/user.json`) — the *historical* official-launcher playtime from Epic's private `library-service` cloud endpoint. A play session is launched by exactly one client, so the two are disjoint and `playtimeMinutes = heroic + cloud` per game, matched on the Epic `appName` (`artifactId` in the cloud response). It owns only `platform: epic` entries, rebuilds them as a marked block last in the file (mirroring the Steam sync), preserves human fields keyed by `appName`, and defaults to played-only (`--include-unplayed` to keep the rest). **No achievements** — Epic closed the achievement-progress API in Jan 2025. `--no-cloud` uses only the Heroic-local data (no token needed); if the cloud token is stale, **open Heroic once** to re-auth, then rerun. Do **not** run `./deploy.sh` after syncing — separate, explicitly-authorized step.

**Syncing GOG — use `scripts/sync-gog.py`** (stdlib only; see `AGENTS.md`). Modelled on the Epic sync — GOG also has **no** Steam-style public API, so it reads what the **Heroic** launcher cached on disk and (optionally) reaches GOG's cloud with the token Heroic stored: the owned library + Heroic-launched playtime (`store_cache/gog_library.json` + `store/timestamp.json`), and — by reusing the GOG OAuth refresh token in `gog_store/auth.json` (Galaxy client id) — GOG's authoritative per-game playtime (`gameplay.gog.com/…/sessions` → `time_sum`) and achievements (`gameplay.gog.com/…/achievements`). **Two differences from Epic:** (1) playtime is **prefer-cloud, NOT summed** — Heroic pushes its sessions up to GOG so the cloud total already contains them, and the script takes `max(cloud, local)` to avoid double-counting; (2) **achievements ARE set** (GOG exposes them, the win over Epic — though sparse until games run through GOG's achievement service). `lastPlayed` comes from Heroic's `store/timestamp.json`, but Heroic frequently records playtime with an empty date (and GOG's playtime API carries no date); as a fallback the script reads the GOG cloud-save sync time from `gog_store/saveTimestamps.json` (`_save_date`), used only when Heroic has no date and only for games that use GOG cloud saves. It owns only `platform: gog` entries, keyed on `appName` (the numeric GOG product id), rebuilds them as a marked block last in the file (after the Steam/Epic blocks), preserves human fields, and defaults to played-only. The cloud is a per-game fan-out (~one request per owned game); `--no-cloud` uses only Heroic-local data (no token). If the token is stale, **open Heroic once** to re-auth. Do **not** run `./deploy.sh` after syncing — separate, explicitly-authorized step.

### Photo dex

A Pokédex-style species checklist at `/gallery/dex/`, layered on top of the gallery rather than beside it: which animals the gallery already contains, and which are still open. Ported from the `animal-dex` proof of concept (`../animal-dex`), but restructured to this repo's conventions — central data file + templates, not one page bundle per species.

**Data**: `data/dex.yaml` — one record per species, 154 of them. Language-neutral facts (`slug`, `number`, `scientific`, `family`, `group`, `difficulty`, `iucn`, `gbif_taxon_key`, `inat_taxon_id`, `wikidata_id`, `height`, `height_measure`, `body_weight`, `diet`, `lifespan`) sit at the top level; anything that reads as prose is nested per language under `names` / `description` / `habitat` / `tips.best_time` / `tips.approach` and **falls back to `en`** (via `layouts/partials/dex-text.html`) when a language is missing. `diet` and `height_measure` are slugs translated through i18n, not free text. `height_measure` (`shoulder` | `standing` | `length` | `wingspan` | `shell`) says *which* dimension `height` is, and renders as a translated parenthetical after the value — "35–50 cm (shoulder)" / "(Schulterhöhe)" / "(skulderhöjd)". It is a slug rather than part of the `height` string precisely because that string is language-neutral: an inline English "(shoulder)" would show up untranslated on the German and Swedish pages. The English label for the row is "Size", not "Height", since for the 82 birds and 8 insects the conventional measure is body length or wingspan, not height (German/Swedish already said Größe/Storlek). Every record with a `height` must have a `height_measure`. **`tips` is currently empty on every species** — the six seeded examples from the animal-dex import were removed as generic advice rather than the author's own field experience. The capability is fully intact: `dex-detail.html` renders the field-notes section only when `tips.best_time` or `tips.approach` has content (per-language, English fallback), the `dex_field_notes` / `dex_best_time` / `dex_approach` i18n keys exist in all three languages, and `tips` is still in `FIELD_ORDER`, so adding a block back to any species makes the section reappear with no code change. The section simply renders on no species today. Optional `sightings: [{lat, lng, label, date}]` are hand-entered — only 13 of 633 gallery photos carry GPS EXIF. `description_source: {en, de, sv}` holds the URL of the exact Wikipedia article each description was abridged from (resolved from Wikidata sitelinks by `dex-enrich.py`); the species page needs it to satisfy CC BY-SA attribution. Each language's description comes from that language's *own* Wikipedia — nothing is machine-translated — so the three are independent: 150 of 154 species have Swedish prose, and the remaining 4 (`red-kangaroo`, `european-mouflon`, `european-polecat`, `alpaca`) fall back to the English text *and* the English credit, which `dex-pages.html` resolves together. `habitat`, unlike `description`, is hand-written and only carries `en` / `de`. The `reference` block carries `credit` (display string) plus the structured `artist` / `license` / `license_url` parts that the schema.org `ImageObject` microdata needs — public-domain files have no `license_url`, and the template omits `itemprop="license"` rather than inventing a deed.

**The join**: `data/gallery.yaml` entries gained an optional `species: <Scientific name>` field (e.g. `species: Vulpes vulpes`) matching `scientific:` in `data/dex.yaml`. **A species counts as photographed when at least one gallery entry carries its scientific name** — there is no separate caught/uncaught flag to keep in sync, and archive photos count (they just sort last). 169 of the 179 `category: animals` photos are tagged, covering 46 of the 154 species. The join deliberately runs on the scientific name, not the `slug`: it makes a gallery entry self-describing without a lookup into `dex.yaml`. The `slug` remains the dex identity — URLs, `assets/data/dex/ranges/<slug>.geojson`, `assets/images/dex/reference/<slug>.jpg`, `--only` flags. Matching is case-insensitive (`dex-index.html` and the `species` filter in `collect-images.html` both lowercase both sides); a value naming no dex species produces a build **warning**, not a failure, and those photos simply do not appear in the dex.

**`layouts/partials/dex-index.html`** is the single join point and the thing to reach for in any new dex template. Called via `partialCached`, it returns `{all, bySlug, caught, total, groups}`; each entry carries `slug`, `scientific`, `number`, `group`, `caught`, `species` (the raw record), `photos` (portfolio → current → archive) and `cover`. `collect-images.html` gained matching `Species` / `Section` / `Portfolio` fields and a `species` filter key — pass `.scientific` to it, which is what `dex-pages.html` puts in `filter_species`.

**`layouts/partials/dex-lookup.html`** maps a scientific name → `{slug, name, url}` for the current language, so a gallery photo can link to the species' dex page: the gallery stores the scientific name while the dex page lives at its slug. Deliberately *not* `dex-index.html`, which joins every species against every photo — a caption link does not need that, and `gallery.html` renders on many pages unrelated to the dex. The lightbox info panel (`assets/js/lightbox.js`) reads `.caption-species` (with `data-dex-url`) and `.caption-software` out of the hidden `.pswp-caption-content` span and renders them as the **Species** (linked) and **Edited with** rows; the labels come from the `speciesLabel` / `softwareLabel` i18n keys passed through the JS params in `head.html`. Items in that span carry `data-field` so the popup labels values by field rather than by document order.

**Pages** are generated by a **content adapter**, not by content files: `content/gallery/dex/_content.{en,de,sv}.gotmpl` each call `layouts/partials/dex-pages.html`, which does the `.AddPage` loop. There is one adapter per language because Hugo scopes an adapter to the language of its filename — a bare `_content.gotmpl` only produces pages for English. Species pages set `params.theme: dex-species` plus `filter_species`/`include_archive`, so the photo strip is the ordinary `gallery.html` partial and inherits PhotoSwipe, the like counters and the EXIF captions for free.

**SEO / structured data**: species pages emit `WebPage` + `about: {@type: Taxon}` from `layouts/partials/templates/schema_json.html` (the taxon facts arrive as `dex_scientific` / `dex_family` / `dex_wikidata` page params from the content adapter). They previously fell through to that file's `BlogPosting` branch, which asserted three untrue things on all 558 species pages: the site owner as `author` of Wikipedia's text, that text as his `articleBody`, and `datePublished: 0001-01-01`. **Do not add a cross-domain `rel=canonical` to Wikipedia or Commons** — that would ask Google to de-index these pages in favour of the source. Attribution is a licensing act and belongs in the page body, which is where it is. Duplicate Wikipedia prose is not penalised, it simply will not rank; the pages' only rankable content is the owner's own (photos, `tips`, `sightings`).

**Theme dispatch**: `dex-home` in `layouts/_default/list.html` → `dex-overview.html`; `dex-species` in **both** `page.html` and `single.html` → `dex-detail.html`. The gallery home has a fourth nav card (`dex_cover` param picks its image, else the first tagged animal photo).

**Map** (`dex-map.html` + `assets/js/dex-map.js`): the default view is **entirely local** — Natural Earth land/borders drawn as GeoJSON instead of raster tiles, plus the species' simplified iNaturalist range and any sighting pins. A species page therefore makes **zero third-party requests** on load, which is what makes it usable on the Tor onion build. A "detailed map" button is the explicit opt-in that swaps the drawn world for OpenStreetMap tiles + the GBIF density overlay; the range polygon stays on top in both modes. Leaflet is already vendored at `/packages/leaflet/` and is loaded per-page from `head.html`, not site-wide.

Three things in that file are load-bearing and easy to break:
- **Every vector layer is drawn at three longitude offsets** (`COPIES = [-360, 0, 360]`). A raster base repeats forever but a GeoJSON world is drawn once, so land, borders, ocean and range must all be duplicated together — duplicating only the range leaves its copies floating over empty sea at the edges of a zoomed-out map. Panning is capped at ±360° so there is always a further copy past the edge, and `worldCopyJump` is **off** (it would snap the view for no gain now that the overlays exist in every copy).
- **Stacking order is pinned by panes**, not by load order: `dex-land` 410 → `dex-range` 420 → `dex-ocean` 430 → `dex-lines` 440. These are independent fetches that finish in any order, and a shared renderer paints as layers arrive — which once put the range *underneath* the land, visible only over the sea.
- **The ocean layer is a mask.** iNaturalist's geomodel is a thresholded prediction raster, so a widespread terrestrial species' polygon genuinely covers open water (wild boar contains the north Pacific in the raw source data — this is not a simplification artifact). Repainting the ocean over the range clips it to the coastline. Species with `marine: true` in `data/dex.yaml` skip that layer, or whales, seals, sea turtles and penguins would be masked down to nothing — 17 species carry the flag.

**Committed assets** (unlike gallery photos, these *are* in git): `assets/data/dex/world-{land,borders}.geojson` (Natural Earth, public domain, ~215 KB), `assets/data/dex/ranges/<slug>.geojson` (iNaturalist, CC BY 4.0, 150 species, ~4.5 MB — simplified and coordinate-rounded to fit a 45 KB per-species budget), and `assets/images/dex/reference/<slug>.jpg` (Wikimedia Commons stand-ins, 108 files / ~21 MB, fetched only for species with no photo of the user's own, always rendered dimmed and credited). These are fetched at `--width 900`, which Commons delivers as ~960px — deliberately matching the `fill 900x900` a real hero photo gets, because the hero slot is only 300–320 CSS px and a 320px stand-in looked visibly softer than the owner's own photos on any HiDPI screen. Commons snaps thumbnail widths **up** to cached buckets (~500 / 960 / 1280 for these files), so 900 and 500 are the only two settings worth using. `dex-detail.html` caps the render at `min(width, height, 900)` so a low-resolution stand-in is never upscaled — a square `fill` is limited by the *shorter* side, and most Commons photos are landscape, so 73 of the 108 land in the 640–899 band rather than at a full 900.

**Scripts** (stdlib only, sharing `scripts/dex_common.py` for the YAML reader/writer): `dex-import.py` (one-shot animal-dex import), `dex-add.py` (add one species by hand, auto-numbered), `dex-tag-photos.py` (propose `species:` for gallery photos; carries a `MANUAL` table of visually identified files and refuses to guess), `dex-enrich.py` (fill *empty* fields only, from GBIF/Wikidata/Wikipedia), `dex-ranges.py`, `dex-covers.py`, `dex-renumber.py` (close gaps in `number` after a removal; preserves the existing order). Full workflow in `AGENTS.md`. Styles are `assets/css/extended/dex.css`; i18n lives under the `# Photo dex` block in `i18n/{en,de,sv}.yaml`.

### Models

A page per person in front of the camera, at `/gallery/models/<slug>/`. It is layered on the gallery the way the dex is — the species design with the nouns swapped — plus the one thing a species does not have: a species cannot change its name, withdraw consent or ask to be forgotten. The reasoning is in `docs/concepts/gallery-models.md`; three questions that concept left open were settled in the build. The section is **`model` / `/gallery/models/`**, not `people` — the photographic term, and the one a *model release* is named after. The gallery home got **no** nav card: the section is reached from the photos that show a person and through the site search, which is as much promotion as a page about someone else's face should get from the gallery's front door. And the licence default was **not** changed: `all-rights-reserved` is not enforced anywhere in the build, and the rights problem is carried by a sentence of text instead (below).

- **Data**: `data/models.yaml`, one record per person. The header comment in that file is the schema reference and is worth reading before editing it. `slug`, `name` and `visibility` are **required**; `consent` (a date — **never rendered**, a note to the author rather than a release store), `bio`, `links` and `cover` are optional. `bio` is per-language (`{en, de, sv}`, or a bare string meaning English — `model-pages.html` normalises the string form before handing it over, because `dex-text.html` *indexes* the field and `index "a string" "de"` is a build error rather than an empty result) and is read through **`dex-text.html`**, so it inherits the same English fallback the dex prose uses and a bio written in one language still renders on all three pages. `links` is `[{name, url}]` where `name` is an icon key `layouts/partials/svg.html` already knows (~150 platforms, chain-link glyph for the rest). `cover` is a gallery photo **UUID**, resolved through `gallery-meta.html`'s `byId`; a uuid that resolves to no photo is a build error rather than a silent fallback, because it is always a typo. **The display name lives in this file and nowhere else** — the photos carry only the slug, so a change of name is a one-line edit instead of a sweep through 650 photo entries. Two things must never go in the file: contact details of any kind (the repository is public, so every line of it is page content whether it was meant that way or not), and anything the person did not agree to have published.
- **`visibility` is required, has no default, and each value is one whole behaviour** rather than a bundle of flags to keep in step — a record that omits it, or misspells it, is a hard build error naming the record and the value, because consent is a decision somebody made and not something a template may assume. **Both gates are allowlists** (`in (slice "public" "unlisted")`), never `ne "hidden"`, and that is load-bearing: `errorf` marks a build failed but **does not stop template execution** (the same note is in `collect-images.html`), so with a denylist a misspelled `visibility: hiden` would render the page and write the name into `public/` on the way to a failing build. Only `deploy.sh`'s `set -e` would have stopped it shipping. The rule this feature exists to enforce fails **closed**: anything that is not exactly `public` or `unlisted` renders nothing.
  - `public` — page rendered, listed in the `/gallery/models/` grid, indexed, name shown on every photo.
  - `unlisted` — page rendered and reachable by URL, but not listed: the adapter sets `build: {list: never}` plus `robotsNoIndex` and `searchHidden`, which is the Nicklheim-album pattern driven from the adapter instead of front matter. Verified on Hugo 0.166.0: `build` **is** a valid top-level key of `.AddPage` (like `aliases`, unlike params), and `list: never` with `render: always` keeps the page out of `.RegularPages`, the section RSS, the search index (`index.json`) and `sitemap.xml` while leaving the URL reachable. An unlisted page is still linked from the photos that show the person — `unlisted` means "not in a listing", not "unreachable", and the photo pages that link to it are indexed anyway.
  - `hidden` — no page at all, and the name appears **nowhere** in `public/`: not on a photo, not in a caption, not as a slug. Verified against a real build.
- **`hidden` is the tombstone, and deleting a record is a build error on purpose.** Removing a person is *not* done by deleting their record: the photos still carry the slug, `gallery-meta.html` stops the build on it, and that is the correct outcome — the photos themselves still need a decision (stay, move to the archive, or leave the photo store), which is a separate per-case call this feature deliberately does not make. `visibility: hidden` makes the person vanish from every rendered page in one edit and keeps the slug reserved so it is never reused by someone else. **A hidden record may be `slug:` + `visibility:` and nothing else** — `name:` is required only on a record that renders. This file is public on GitHub, history included, so a tombstone forced to keep the name would take it off the site and leave it in the repository forever, which is not what someone asking to be forgotten asked for.
- **The join is a slug on the photo, never a name.** `model: jane-doe` in `data/gallery.yaml` (string or list — a group photo names everyone in it, the same shape as `project:`). The species join runs on the scientific name because that name is stable, self-describing and has an external authority; a person's name is none of those — people marry, transition, adopt a stage name — so the photo stores the identity and the display name is looked up. `gallery-meta.html` normalises `model:` into a derived **`.models`** slice exactly as it does `project:` → `.projects`, with the same rule: filter with `in $meta.models $slug`, never `in` on the raw string. `collect-images.html` exposes it as **`.Models`** with a `model` filter key beside `species` — `.Models`, not `.Model`, because the collector already returns `.CameraModel` from EXIF, whose tag is literally called `Model`.
- **An unknown `model:` slug is a hard build error**, where an unknown `species:` is only a warning. That asymmetry is deliberate: species names are an open external vocabulary and a photo may legitimately be tagged before the species is added, while model slugs are a small closed set the author invented himself, so a miss is always a typo — and the cost of a silent miss is a person losing the credit or the visibility setting they agreed to. `gallery-meta.html` validates the whole of `data/models.yaml` up front (missing `slug`, missing `name`, **duplicate slug**, missing or invalid `visibility`) before it walks the photos, then errors on any `model:` value that is not one of those slugs, naming the photo file and the value.
- **Two partials, and they are two for the reason the dex pair is two**:
  - **`layouts/partials/model-index.html`** is the join, `partialCached` **per language**. It reads `gallery-collected.html` — already cached, already carrying every photo with its EXIF and language-resolved prose — so the join costs one walk over a list in memory and no image processing. Returns `{all, bySlug, listed, total}`; each entry carries `slug`, `name`, `record`, `visibility`, `photos` (portfolio first, newest within each band), `count`, `cover`, `hasPage` and `listed`. Only records that render a page are in `all`; `listed` is the `public` subset, which is what the grid and the nav card read.
  - **`layouts/partials/model-lookup.html`** is the cheap one, slug → `{name, url}` for the current language, with the URL resolved through `site.GetPage` so the link survives the section moving. `gallery.html` renders on every grid, every album, every dex species page and every photo page, and a caption needs a name and a URL — making it depend on the whole-gallery join for one string is the mistake `dex-lookup.html` exists to avoid. **The absence of an entry means print nothing.** This is the one place it differs from `dex-lookup.html`, where a species the dex does not know still prints its scientific name as plain text: a `hidden` record, a record whose page was never generated, and a slug the lookup has never heard of all render as **no row at all**. The name is never derived from the slug, and no caller may invent one.
- **Archive photos do not count for a model** — unlike the dex, where they do. "Have I photographed this species" is a question about the whole body of work, so the dex counts retired shots; a person's page is a page that is published *today*, and the archive is where retired shots go. `model-index.html` skips `section: archive` before it groups, `gallery.html` never sets `include_archive` on a model page, and **a record whose photos are all archived therefore renders no page at all** — as does a record with no photos, since a page that is a name and a link list with nothing to show has no purpose (there is no "uncaught" state here, unlike a dex species).
- **Pages come from a content adapter**, like the dex and unlike the per-photo pages: `content/gallery/models/_content.{en,de,sv}.gotmpl`, one file per language because Hugo scopes an adapter to the language of its filename, each calling `layouts/partials/model-pages.html`, which does the `.AddPage` loop over `model-index.html`'s `all`. **All three languages**, because a model page has the bio, which the author writes and can translate. The slug is language-neutral, so the three share a URL segment and are linked through `translationKey: model-<slug>`. The section index is a plain `content/gallery/models/_index.{en,de,sv}.md` stub with `params.theme: models-home`.
- **Theme dispatch lives in both `layouts/_default/page.html` and `layouts/_default/single.html`** for theme `model` (the dex species pages need the same pair, for the same Hugo 0.146+ template-system reason — see memory `reference_template_dispatch.md`), and `models-home` is dispatched in `layouts/_default/list.html`. **The gallery home deliberately does not link it** — there are three nav cards (Projects / Dex / All Photos), not four. `/gallery/models/` is entered from a photo that shows the person, from the site search, or by URL. If that is ever revisited, the card must stay conditional on `model-index.html` having a `listed` record: this section is built from `data/models.yaml` and can legitimately be empty, unlike the other three, and a card onto an empty grid is worse than no card. `list.html` carries a comment at the spot saying so. Because the search is then the section's *only* way in, `layouts/_default/index.json` adds `/gallery/models/` to the search index explicitly — branch pages are not in `site.RegularPages` and would otherwise be unsearchable, the same reason `/travel` is added there — guarded on `model-index.html` having a `listed` record, since a search hit landing on an empty grid is the same mistake as a nav card onto one. The individual model pages need no such help; they are ordinary regular pages.
- **`layouts/partials/model-detail.html`** renders the page: breadcrumb, `fill 900x900` hero from `cover`, the name as H1, the bio as `.Content` (nothing at all when empty — a placeholder line about a person is worse than no line), the links, the photo strip and the rights note. The strip is the ordinary **`gallery.html`** driven by the page's `filter_model` param, so PhotoSwipe, the like counters, the EXIF captions and the `ImageObject` microdata come for free — the same move `dex-detail.html` makes. `layouts/partials/model-card.html` is one tile of the grid.
- **Where the model row appears**: the `gallery.html` grid caption and the `gallery-photo.html` hero each emit one `<span class="caption-model" data-field="model" data-model-url="…">` per person inside the hidden `.pswp-caption-content`, after `.caption-species`; `assets/js/lightbox.js` reads those spans and renders a linked **Model** / **Models** section under Species (label picked by count, from the `modelLabel` / `modelsLabel` i18n keys passed through the JS params in `head.html`); `photo-meta.html` prints a `photo-model` row on the photo page — resolved by the *caller*, not by that partial, precisely because "resolves to nothing" is a meaningful state that must produce no row; and `gallery-photo.html`'s **"Appears in"** list links the model page(s) after the dex link. `gallery.html` hoists the lookup out of its loop because that range runs once per photo on the general grid.
- **Structured data**: a `ProfilePage` branch in `layouts/partials/templates/schema_json.html` emits `mainEntity: Person {name, image, sameAs: [links]}` for theme `model`. Without it the page fell through to that file's `BlogPosting` branch, which would claim the site owner as `author` of somebody else's bio and stamp `datePublished: 0001-01-01` on it — the same bug the dex and the photo pages each had to fix. The photo `ImageObject` gains `about: [{@type: Person, name, url}]`, built from `model-lookup.html` so it names **only people the rendered page already names visibly** — structured data must never say more about a person than the page does, which is what makes a `hidden` record invisible there too.
- **`rel="noopener"` on the model's links, and never `rel="me"`.** PaperMod's `social_icons.html` emits `rel="me"` because those are the *site owner's* profiles and `rel=me` is an identity claim about the site's author; a model page links to somebody else, so making that claim would be false. That is also why `social_icons.html` is not reused (it iterates `site.Params.socialIcons` rather than an argument). The honest place for those URLs is `sameAs` in the `ProfilePage` JSON-LD, which is a statement about the *Person*, not about the author.
- **There is deliberately no rights notice on the page.** An earlier revision printed one translated sentence on the model page and in the licence section of any photo page with a model, saying that the licence covers the photograph and grants nothing over the depicted person. The site owner decided against it and it was removed — markup, CSS and the `models_rights_note` i18n keys. **This was a decision, not an oversight; do not re-add it unasked.** The reasoning it carried still holds and is worth knowing: a photo licence covers the **photographer's copyright and nothing else** — Creative Commons' own FAQ says its licences do not touch publicity, privacy or personality rights, and German law (§22 KUG, GDPR on top for the name-to-likeness link) says the same from the other side, so a CC BY-SA portrait is a photo anyone may adapt and republish of a person who consented only to this site. `all-rights-reserved` is already a key in `data/licenseMap.yaml` and is the per-photo lever for that; it is **not** enforced by the build, so it is set deliberately or not at all.
- The section stubs set **`outputs: [HTML]`**: `layouts/_default/rss.xml` branches on `eq .Section "gallery"`, so every section below `/gallery/` otherwise emits the *same* 572-photo feed — 636 KB per language per build, with `<link>`s pointing at `/gallery/models/#<uuid>`, anchors that do not exist on that page. (`/gallery/dex/` and `/gallery/projects/` still do this; only the new section was fixed.) The model's links carry **no `safeURL`**, unlike `social_icons.html`: that partial serves the owner's own config, this one serves whatever a third party handed the author, and `safeURL` switches Hugo's scheme filter off — without it a `javascript:`/`data:` URL renders as `#ZgotmplZ` instead of executing. `gallery-portfolio.html` emits the caption spans too, not just `gallery.html` — the portfolio is the grid the gallery home leads with, and leaving it out meant the Model row appeared everywhere except the most-seen page. i18n lives under the `# Models` block in `i18n/{en,de,sv}.yaml`; styles are `assets/css/extended/models.css` (auto-bundled, PaperMod theme variables only, no palette of its own, and it also holds the `.photo-model` rule the photo page uses). That same commit added **`photoCount` and `albumCount` to `i18n/sv.yaml`**, where they had been missing entirely — every Swedish gallery count had been silently falling back to the English string.

### i18n

UI strings in `i18n/{en,de,sv}.yaml`. Per-language menus, descriptions, and home content live under `languages.<lang>.params` in `hugo.yaml`. Content files use `index.<lang>.md` for branch bundles and `_index.<lang>.md` for sections.

## Conventions worth knowing

- Use Hugo image processing (`images.Process`, `images.AutoOrient`) — never reference raw image URLs directly, and always `AutoOrient` first so EXIF rotation is applied.
- New gallery images: drop the file into the photo store (the gallery mount source), then add a matching entry to `data/gallery.yaml` **including a UUID `id`** (the build will hard-fail without one — `scripts/add-gallery-ids.py` populates missing ids in bulk).
- Renaming an existing gallery image: rename the file in the photo store (the gallery mount source) and update only the matching `src:` in `data/gallery.yaml`. Do not touch `id` — deep links, the likes API key, and any `featured_image:` referencing it all use the id.
- New license values must be added to `data/licenseMap.yaml` — as a **key** with `url`, `label` and `terms` — or the build will `errorf`. Write `license: <key>` in `data/gallery.yaml`, not the display string.
- A new photo's entry is best created with `python3 scripts/sync-gallery.py`, which appends a stub and pre-fills `title` / `alt` / `description` / `license` / `artist` from what darktable wrote into the file. That read happens **once, at stub time** — the build never looks at those tags again, so a later re-export cannot change what the site says about a photo.
- `security.txt` (RFC 9116) is **generated, not static** — `layouts/_default/home.securitytxt.txt` plus the `securitytxt` output format in `hugo.yaml`. It was a static file whose `Expires` sat four months in the past before anyone noticed; generating it refreshes the date on every build (build day + 1 year - 1 day, so it stays inside the RFC's "less than a year" recommendation, truncated to whole days so rebuilds are byte-identical). Two things are load-bearing: the format's `path` is `../.well-known` because `path` resolves relative to the **language** directory and the file must sit at the domain root, and it is listed under `languages.en.outputs.home` **only** — putting it in the top-level `outputs` makes all three languages write the same target path. `Canonical` uses `absURL`, so the Tor build in `deploy.sh` emits the onion URL instead of the clearnet one. Do not re-add `static/.well-known/security.txt`; a static file of the same name would collide with the generated one.
- Adding a model: write the record in `data/models.yaml` **first** (`slug`, `name`, and an explicit `visibility:` — the build errors without one), then add `model: <slug>` to the photo entries in `data/gallery.yaml`. A slug with no record is a hard build error; removing someone is `visibility: hidden`, never a deleted record. Set `artist:` on any photo the owner did not take — it otherwise resolves to the site author. Full workflow in `AGENTS.md`.
- Gallery scripting/migration helpers are written in Python (per project memory).
