# Photo page URLs

Every photo gets its own page at `/<lang>/gallery/photo/<slug>/`, generated by the content adapters under `content/gallery/photo/` via `layouts/partials/gallery-photo-pages.html`. The slug is computed in `gallery-meta.html`:

```
slug = urlize( entry.slug  ||  title[lang] || title.en )
```

- **Per language.** The three languages get three different segments (`tree-cover-alpaca-peeking-out-from-behind-a-trunk` / `deckung-am-baum-alpaka-lugt-hinter-einem-stamm-hervor` / `skydd-vid-tradet-alpacka-kikar-fram-bakom-en-stam`), linked through `translationKey: photo-<uuid>`. This works because the partial cache is per-language — see `gallery-meta.html` in `docs/gallery/overview.md`.
- **From the title, not the filename.** It used to be the filename stem, but 65% of those are camera output (`DSC_2632`, `P1017063`), so most URLs carried no information. The old objection — prose lived in the image's XMP, so a darktable re-export would silently move a URL — died with the one-time metadata import: titles live in `data/gallery.yaml` now and the build never reads the file's XMP again.
- **A missing title is a hard build error**, naming the photo and the language. There is deliberately no filename fallback: after every photo was given a title in all three languages, silently regressing one URL to `dsc-2632` is the failure nobody would notice. `scripts/sync-gallery.py` writes empty `title:` slots in all three languages, so a new photo stops the build until its title is written — which is the reminder, and the only place a title is typed.
- **Transliteration is per language** — `gallery-meta.html`'s `$translit`, branched on `$lang`. German expands the umlaut the way DIN 5007-2 does (`Porträt` → `portraet`, `grünen` → `gruenen`, `weißen` → `weissen`); Swedish and English fold it away (`över` → `over`, `Ardèche` → `ardeche`), because in Swedish `ä ö å` are letters in their own right rather than decorated vowels and the expansion reads as German there. Both tables are written out in full, shared tail included: Hugo's `append` on a slice of slices appends the inner slice as a single element, so composing them from a common tail does not work. Verified across all photos with both tables: zero collisions in any language — expansion can only reduce collisions, and the folding side does not merge anything either.
- **Two things absorb a reworded title moving a URL**: each page keeps a permanent `/gallery/photo/<uuid>/` alias, and `slugAliases:` on the entry holds the URLs it used to have. Both are emitted as redirects; an alias equal to the current language's slug is skipped, or Hugo would write a redirect over the page it redirects to.
- **`slugAliases:` is frozen, never recomputed.** The one-time filename→title migration wrote each photo's old filename-derived segment onto all 648 entries; the migration script was a throwaway and is gone, the data file is the record. An alias exists to keep a dead URL alive, so it must not follow the filename it came from — rename the photo later and the alias stays put. Hand-edit it to preserve a URL after a rewording.
- `slug:` on an entry still pins one segment **language-neutrally** and opts out of the whole mechanism. It is set on no entry today.

## A reworded English title

The English title decides the photo's page URL **and** its image file names. After
rewording one: add the old English page slug to the entry's `slugAliases:` (keeps
the old page URL and, through the nginx redirect map, the old image URLs alive),
then `npm run golden:update`.
