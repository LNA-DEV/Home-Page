# Inlining a gallery photo in a post

`layouts/shortcodes/galleryImage.html` puts one gallery photo into a post body, addressed by its **UUID** from `data/gallery.yaml` (`{{< galleryImage id="…" >}}`) — the id rather than the filename, so a rename in the photo store does not break the post. It resolves the photo through `collect-images.html` (new `id` filter key; pass `excludeArchive false` with it, as the shortcode does, since naming a photo by hand is explicit), so an inlined photo carries exactly the metadata the gallery shows. An unknown id is a **hard build error** with file:line, not a silent blank.

Rendering is one fixed path: width-constrained `fit` variants at 480/720/1080/1440 px through `image-variant.html` (AutoOrient included, one chain) — capped at the oriented original width so a small file is never upscaled, and a photo narrower than 480 px gets one variant at its own width — with `src` pointing at the 720 px variant (`--main-width`), `sizes="(max-width: 720px) 100vw, 720px"`, and `width`/`height` set against layout shift. The height bound in the `fit` spec is deliberately 10× the width so tall portraits stay full-width instead of being shrunk to a square, unlike the gallery grid's `fit 600x600`.

Both caption lines are **off by default** (`showTitle`, `showExif`; `caption="…"` overrides). `alt` and `title` come from `data/gallery.yaml` resolved into the post's language, so a German or Swedish post only needs `alt="…"` / `caption="…"` where that photo has no translation yet or the post wants different wording. The default link is a deep link to `/gallery/general/#<uuid>` (or `/gallery/archive/` for archived photos) resolved via `site.GetPage`, which is language-correct and survives the gallery moving; `lightbox.js` matches `window.location.hash` against the `data-id` there and opens PhotoSwipe. `link="false"` renders no link. There is **no per-category gallery page** — `/gallery/general/` holds every non-archive photo. SEO markup mirrors `gallery.html`: schema.org `ImageObject` microdata with license, creator, credit and copyright. Styles are `assets/css/extended/galleryImage.css`.

`layouts/shortcodes/galleryImageText.html` is the paired variant: a photo beside its text, in a block that breaks out of the 720px column to `--width-wide` (1060px, the header's width). It exists because a 45% photo *inside* 720px leaves a ~372px text column (~41 characters), which the theme's `word-break: break-word` then splits German compounds across; at the header width it measures 466px photo / 570px text, ~63 characters. The breakout is the `l-wide` layout class (`docs/design-system.md`): `--width-wide` capped at `100vw - 2 × gutter`, because `100vw` includes the scrollbar. It stacks below **900px**, not the theme's 768px breakpoint — at 768px the text track is back to ~44 characters — and the photo always comes first when stacked, whichever `align` it has on desktop. `galleryImage` also takes `align="left|right"`, which floats the photo so **ordinary Markdown paragraphs wrap around it** — no moving prose into a shortcode, which is the usual case for a photo essay and the reason `galleryImageText` is the exception rather than the default. The float is pulled into the margin between `--main-width` and `--nav-width` (170px per side): a 340px photo then eats only 170px of the text column, leaving ~58 characters instead of the ~41 an in-column float would. The negative margin is clamped to `min(170px, (100vw - main - 2*gap) / 2)` — below ~1108px viewport that margin does not exist yet, and a fixed -170px would push the photo off-screen. Headings do **not** clear the float — a heading sets beside a photo exactly as a paragraph does, so a whole section can run alongside a tall portrait. (They used to carry `clear: both`; that left ~270px of dead space whenever the wrapping text was shorter than the photo, and letting the next section flow into it is the only way to fill it. PaperMod gives headings no border or background, so a shortened heading line shows no seam.) Full-width `figure`s do still clear — see `assets/css/extended/img-shortcode.css` — because a figure's `<img>` is 100% of the figure width and would run straight through the float instead of wrapping. `size` tunes the width per call — `small` (280px) / `medium` (340px, default) / `large` (420px), or a bare pixel number — and works without `align` too, where it caps and centres an otherwise full-width photo. The resolved pixel value drives **both** the CSS `--img-width` and the `sizes` attribute from one place, so a smaller photo actually downloads a smaller file instead of being scaled down in CSS; an unknown value is a hard build error.

Both shortcodes share `layouts/partials/gallery-image-figure.html`; the only things that differ are the CSS class and `sizes`.
