# Concept: models — a page per person in front of the camera

**Status:** concept, nothing implemented. No build has been run against it.
**Read against:** the working tree of 2026-09-18 (Hugo 0.166.0), `data/gallery.yaml` at 648 photos, after the per-photo pages landed (see `gallery-photo-pages.md`).

A gallery photo can already say *what* it shows (`species:`), and that one field gives it a link into the dex, a filtered photo strip, and a labelled row in the lightbox. This adds the same for *who* it shows: a `model:` field on the photo, a `data/models.yaml` with one record per person, a page per model at `/gallery/models/<slug>/` with their photos, a short bio and their social links, and a linked **Model** row wherever the species row already appears.

The design is deliberately the species design with the nouns swapped. The one place it is *not* is where a species and a person differ: a species cannot withdraw consent, change its name, or ask to be forgotten. §3 is about that.

## Settled decisions

| | |
|---|---|
| Join key | A **slug** on the photo (`model: jane-doe`), never a name — see §2 |
| Cardinality | String or list, like `project:` — a group photo names everyone in it |
| Data | `data/models.yaml`, one record per person; display name, bio, links, cover live there, not on the photo |
| URL | `/gallery/models/<slug>/`, all three languages, generated by a content adapter like the dex |
| Consent state | An explicit, required `visibility:` on every record — `public` / `unlisted` / `hidden`. No default. |
| Unknown slug | Hard build error, not a warning — see §2 |
| Photos shown | Non-archive only, as on a project album; the archive is where retired shots go |
| A record with no photos | Renders no page |
| Name display | A person's name appears on the site **only** through a published record. No fallback to the raw slug, ever. |

## Decisions still open

| | |
|---|---|
| Naming | `model` / `/gallery/models/` (the photographic term, and the one a *model release* is named after) or `people` / `/gallery/people/` (neutral, covers friends and self-portraits). Search-and-replace before step 1; nothing else depends on it. |
| Gallery home | Add a fifth nav card next to Projects / Dex / All Photos, or leave the section reachable only from photos until it has more than a couple of people? |
| Licence default | Whether model photos should default to `all rights reserved` rather than the gallery's CC BY-SA — §3 |

## 1. What the data supports today

Measured against `data/gallery.yaml`:

| | of 648 |
|---|---:|
| `category: portrait` | **5** |
| … with a title, alt text or tags | **0** |
| … with a licence and artist set | 1 (`MaskMan.JPG`, CC BY-SA) |
| `species:` set (the precedent) | 172 |
| `project:` in list form (the precedent for multi-valued fields) | 17 |
| `artist:` naming someone other than the site owner | 0 |

So this starts from nothing: five candidate photos, none of them tagged, described or titled. That is fine — the feature is for photos that do not exist yet — but it fixes two things about the design. The `model:` field must be **optional with no migration**, exactly as `species:` was; and there is no data to measure a threshold against, so the rules in this document come from the species precedent and from the consent problem, not from the corpus.

The last row matters for the example the request used: `lukas-nagel` as a model means a photo the site owner did **not** take. `collect-images.html` already resolves the photographer as `yaml.artist → EXIF Artist → site.Params.author.name`, so crediting the actual photographer is one `artist:` line on the photo. Nothing new is needed for it — but it must be set, or the page will credit the owner for a photo of himself taken by someone else.

## 2. Identity — a slug, joined and validated

```yaml
# data/gallery.yaml
- id: e2809038-df5a-4bc4-af08-d69df91c400f
  src: MaskMan.JPG
  category: portrait
  model: jane-doe            # or: [jane-doe, john-roe]
  artist: Lukas Nagel
```

The species join runs on the scientific name because that name is stable, self-describing and has an external authority. A person's name is none of those: people marry, transition, adopt a stage name, or ask to be called something else — and every one of those must be a one-line edit in `models.yaml`, not a sweep through the photo file. So the photo carries a **slug** and nothing else; the display name lives in exactly one place.

`gallery-meta.html` normalises `model:` into a `.models` slice the way it already turns `project:` into `.projects`, and `collect-images.html` exposes it as **`.Models`** with a `model` filter key beside `species`. Not `.Model`: the collector already returns `.CameraModel` from EXIF, whose tag is literally called `Model`, and a bare `.Model` next to it would be misread.

### Unknown slug: error, not warning

A `species:` value naming nothing in the dex is a build *warning*, and that is right for it — the photo may be tagged before the species is added, and a mistagged animal is still a good gallery photo. A `model:` slug naming nothing in `models.yaml` is different: the slugs are a small, closed set the author invented, so a miss is always a typo, and the *cost* of a miss is a person silently losing their credit. `gallery-meta.html` already hard-fails on a missing `id` and a duplicate slug; the unknown model slug joins that list, with file and value in the message.

Removing a person is therefore **not** done by deleting their record — see `hidden` in §3. A deleted record with photos still pointing at it fails the build, which is the correct outcome: the photos still need a decision.

## 3. Consent — the part that is not a copy of the dex

Linking a recognisable face to a name and a list of social profiles creates a searchable identity page. In Germany that sits under §22 KUG (a recognisable person's image may be published only with their consent) with the GDPR on top for the name-to-likeness link, and the moral version of the same rule holds everywhere: the person gets to say yes, and gets to change their mind later. The design has to make that state explicit and make changing it cheap.

```yaml
# data/models.yaml
models:
- slug: jane-doe                 # URL segment + the key photos join on; never changes
  name: Jane Doe                 # display name; change freely
  visibility: public             # REQUIRED — public | unlisted | hidden
  consent: "2026-08-14"          # date the release / consent was given
  bio:                           # per language, English fallback via dex-text.html
    en: "…"
    de: "…"
  links:                         # rendered through svg.html, same shape as the persons on /links/
    - name: instagram
      url: "https://…"
    - name: website
      url: "https://…"
  cover: 0c16ee6e-67b6-4cb0-9812-162da7df7922   # optional; a gallery uuid. Else the first portfolio photo, else the newest.
```

**`visibility` is required and has no default.** Each value is one whole behaviour, not a bundle of flags to keep in sync:

| | Page | Listed on `/gallery/models/` | Sitemap / search / robots | Name + link on photos |
|---|---|---|---|---|
| `public` | rendered | yes | indexed | yes |
| `unlisted` | rendered | no | `build.list: never` + `robotsNoIndex` + `searchHidden` — the Nicklheim-album pattern, driven from the adapter | yes |
| `hidden` | none | no | — | **none** — not the name, not the slug, nothing |

`hidden` is the tombstone: the record stays so the slug is never reused, the photos keep their `model:` and keep building, and the person vanishes from every rendered page in one edit. Whether the photos themselves then stay in the gallery, move to the archive or leave the photo store is a separate, per-case decision using the workflows that already exist — this concept manages the *name*, not the files.

`unlisted` exists for the same reason the Nicklheim album is unlisted: a page can be fine to show to someone who was handed the link, or who arrived from a photo, without being something a search engine should surface. It is not privacy — the photo pages that link to it are indexed — but it is the honest middle setting.

**Two things deliberately not in the file.** No contact details of any kind — the repository is public on GitHub, so `models.yaml` is public too, and everything in it must be something that may appear on the page. And no `rel="me"` on the links: PaperMod's `social_icons.html` emits it because those are the *owner's* profiles, and `rel=me` is an identity claim about the site's author. A model page links to someone else, so it uses `rel="noopener"` and nothing more — which is also why `social_icons.html` is not reused (it also iterates `site.Params.socialIcons`, not an argument).

**The licence line.** The gallery's photos are CC BY-SA, and `MaskMan.JPG` — the one tagged portrait today — is too. That licence covers the photographer's copyright and nothing else; Creative Commons' own FAQ says the licences do not touch publicity, privacy or personality rights, and German law agrees. A CC BY-SA portrait is therefore a photo anyone may adapt and republish *of a person who has consented only to this site*. Two consequences: the model page and any photo page with a model carry one translated sentence saying the licence does not cover the depicted person's likeness; and `all rights reserved` — already in `data/licenseMap.yaml` — is the sensible per-photo default for model work. Whether to make it the rule is the open decision above.

## 4. Generation — a content adapter, exactly like the dex

`content/gallery/models/_content.{en,de,sv}.gotmpl`, one per language because Hugo scopes an adapter to the language of its filename, each calling a shared `layouts/partials/model-pages.html`. That partial reads `model-index.html` (§5) and emits one `.AddPage` per record that is `public` or `unlisted` **and** has at least one non-archive photo:

```go-html-template
{{ $.AddPage (dict
  "path"    .slug
  "kind"    "page"
  "title"   .name
  "content" (dict "mediaType" "text/markdown" "value" $bio)
  "build"   (dict "list" (cond $unlisted "never" "always") "render" "always")
  "params"  (dict
    "theme"          "model"
    "model_slug"     .slug
    "filter_model"   .slug
    "translationKey" (printf "model-%s" .slug)
    "robotsNoIndex"  $unlisted
    "searchHidden"   $unlisted
    "hideMeta"       true)
) }}
```

`build` is a documented top-level key of `AddPage`, the same options the Nicklheim album sets in front matter; `aliases` on the photo pages proved that top-level keys work on 0.166 where params do not. Verify `build` the same way in step 3 — it is the one Hugo behaviour this concept leans on that the tree has not exercised yet. `list: never` is what keeps an unlisted page out of the section's `RegularPages` (and so out of the `/gallery/models/` grid and the section RSS) and out of the sitemap.

**All three languages**, unlike the photo pages and like the dex. The photo pages are English-only because they had no per-language prose to justify three copies; a model page has the bio, which the author writes himself and can translate. `dex-text.html` already does the per-language read with English fallback and takes any `{en, de, sv}` map, so a bio present in one language still renders everywhere.

The section index `/gallery/models/` is a `content/gallery/models/_index.{en,de,sv}.md` stub with `params.theme: models-home`, rendered by `list.html` as a card grid over `model-index.html` — public records only, since `unlisted` ones are excluded by `list: never` anyway. A record with zero non-archive photos produces no page and no card: unlike an uncaught dex species, an empty model page has no purpose.

## 5. Partials — two, mirroring the dex pair

**`model-index.html`** is the join, called through `partialCached` per language. It reads `gallery-collected.html` — already cached, already carrying every photo with EXIF resolved — so the join adds no image processing and no second walk over the store. It returns `{all, bySlug}`; each entry carries `slug`, `record`, `photos` (non-archive, portfolio first, then newest), `cover` (the `cover:` uuid resolved through `byId`, else the first photo) and `count`. `model-pages.html`, `model-detail.html` and the `models-home` grid all read it.

**`model-lookup.html`** is the cheap one, for `gallery.html`: slug → `{name, url}` for the current language, `public` and `unlisted` records only, `url` resolved with `site.GetPage` rather than assembled by hand so the link survives the section moving. It is a copy of `dex-lookup.html` with one difference that matters: where the dex lookup's *absence* makes the caption print the scientific name as plain text, the model lookup's absence prints **nothing**. A `hidden` record, a record with no page, a slug the lookup does not know — all render as no row at all. The name is never a fallback.

Why two partials for what might be three people: `gallery.html` renders on every grid, the photo pages, the dex species pages and every album, and the caption only needs a name and a URL. Making it call the join would make every one of those pages depend on the whole-gallery collection for one string. The dex made the same split for the same reason.

## 6. Anatomy — what is on the pages

### The model page (`model-detail.html`, theme `model`)

| Element | Detail |
|---|---|
| **Breadcrumb** | Gallery / Models / Name — the dex's markup, not `gallery-breadcrumb.html`, which only knows two levels |
| **Hero** | `cover` at `fill 900x900`, the same variant and reasoning as the dex hero (300–320 CSS px slot, sharp on 3×). One new render per model. |
| **Name** | H1 from the record. No pronouns field, no age, no location — the page carries what the person put in their own bio and nothing inferred |
| **Bio** | `.Content`, i.e. the per-language bio through the adapter; renders nothing when empty rather than a placeholder |
| **Links** | `links[]` through `svg.html`, which already knows ~150 platforms including Instagram, TikTok, Threads, X, Bluesky, Mastodon, Pixelfed, Flickr, 500px, Behance, Vimeo and Linktree, and falls back to a chain-link glyph for anything else — which is what `website` on `/links/` already relies on. `rel="noopener"` only. |
| **Photos** | The ordinary `gallery.html` driven by `filter_model`, so PhotoSwipe, likes, EXIF captions and the `ImageObject` microdata come for free — the same move `dex-detail.html` makes. Count and first/last capture date above it, as on a species page. |
| **Rights note** | One translated sentence: the photo licence does not cover the depicted person's likeness |
| **JSON-LD** | `ProfilePage` with `mainEntity: Person {name, image, sameAs: [links]}` — the schema.org shape for exactly this page. Without a branch in `schema_json.html` it falls through to `BlogPosting` and asserts the owner as author of the bio with `datePublished: 0001-01-01`, the same bug the dex and photo pages each had to fix. |

### Wherever the species row already is

| Place | Change |
|---|---|
| `gallery.html` caption | One `<span class="caption-model" data-field="model" data-model-url="…">Name</span>` per model in `.pswp-caption-content`, after `.caption-species`; the same span in `gallery-photo.html`'s hero |
| `lightbox.js` | Reads all `.caption-model` spans and renders a **Model** section (label pluralised by count) with linked names, directly under Species; `modelLabel` / `modelsLabel` join the params in `head.html` |
| `photo-meta.html` | A `photo-model` row mirroring `photo-species`, linked names, no scientific-name slot; plus the rights sentence inside the licence section when the photo has a model |
| `gallery-photo.html` "Appears in" | The model page(s), after the dex link — an internal link into the new section from every photo that belongs there |
| `schema_json.html` `ImageObject` | `about: [{@type: Person, name}]` for each model the page already names visibly. Nothing the page does not show. |

The lightbox and the photo page render their own panels from the same data on purpose — `photo-meta.html` says so in its header — so both get the row and neither is refactored here.

## 7. Relation to `gallery-metadata-single-source.md`

That concept (same day, untracked at the time of writing) sets one rule for the photo file: *everything a person writes lives in `data/gallery.yaml`; everything a camera or Darktable records lives in the original.* `model:` is written by a person and belongs on the YAML side of that line, next to `species`, `project` and `tags` — nothing here pulls against it, and the `{en, de, sv}` nesting it proposes for `title` and `alt` is the same shape `bio` uses.

The two meet at its embedding step, where metadata is written into every file under `public/images/gallery/`. The IPTC standard has fields for exactly this — `XMP-iptcExt:PersonInImage` for the person shown, and the PLUS `ModelReleaseStatus` (`MR-NON` / `MR-UMR` / `MR-LMR`) with `ModelReleaseID` for the release — and `model-index.html` would hand the embedding script both values with no extra join. Two rules if that is ever wired up: write them for **`public`** records only, because a name inside a downloadable file travels further than a name on a page and would silently undo `unlisted` and `hidden`; and write the *display name*, never the slug. Until that step exists, nothing about the person is embedded anywhere, and this concept does not depend on it.

## 8. What this does not do

- **No per-model licence handling.** The rights sentence is text; enforcing `all rights reserved` on model photos would be a rule in `collect-images.html` and is the open decision, not part of the build.
- **No model release storage.** `consent:` is a date, not a document. Signed releases live wherever the author keeps contracts, not in a public repository.
- **No changes to the feed or the RSS.** Adapter pages are not `posts`, so the activity feed never sees them; the section RSS at `/gallery/models/index.xml` will list public model pages by default, which is harmless and can be turned off with `outputs` on the section stub if unwanted.
- **No photographer profiles.** `artist:` stays a string. A page per *photographer* is a different feature with the same shape and could reuse everything here, but the request was about the people in front of the lens.

## 9. Cost

| Dimension | Change | Note |
|---|---|---|
| Rendered pages | + 3 per public/unlisted model with photos, + 3 section indexes | Single digits for the foreseeable future |
| Image variants | + 1 `fill 900x900` per model page, + 1 `fill 480x480` per index card | Nothing re-renders; the grid's 600/1200/4000 variants already exist |
| Build time | ~0 | The join reads `gallery-collected.html`, already cached; `model-lookup.html` reads a data file |
| Data | `data/models.yaml` new; `data/gallery.yaml` gains an optional `model:` on the photos that need it | No migration, no script |

**Do not clear `resources/_gen/images`** to see the new variants; they are generated on the first build that needs them.

## 10. Build order

Each step leaves the site building and nothing user-visible changes until step 3.

1. **Data and validation** — `data/models.yaml` with the schema in §3; `gallery-meta.html` normalises `.models` and hard-fails an unknown slug or a record without `visibility`; `collect-images.html` exposes `.Models` and the `model` filter. Tag `MaskMan.JPG` as the fixture. Confirm a typo fails the build with file and value.
2. **Index and lookup** — `model-index.html` and `model-lookup.html`. Pure partials, called by nothing yet.
3. **Pages** — the three adapters, `model-pages.html`, `model-detail.html`, `models-home` in `list.html`, dispatch of theme `model` in **both** `page.html` and `single.html`, `assets/css/extended/models.css`, i18n block. Verify `build.list: never` on an adapter page actually drops it from `RegularPages` and the sitemap; verify a `hidden` record produces no page and a photo-less record produces no page.
4. **Captions** — the span in `gallery.html` and `gallery-photo.html`, the lightbox section, the `photo-meta.html` row, the "Appears in" link, the `modelLabel` params. Done after step 3 so the links have a target on the first build that emits them.
5. **Structured data** — the `ProfilePage` branch and `about` on the photo `ImageObject`.
6. **Docs** — `CLAUDE.md` gets a "Models" subsection beside the dex; `AGENTS.md` gets "Adding a model" (record, visibility, `artist:` on photos not taken by the owner, `all rights reserved` if chosen).
7. **Verify against a fresh build**, not the long-running server on :1313, which misses new layout files: a public page, an unlisted page reachable by URL but absent from the grid and `sitemap.xml`, a `hidden` record with no trace in `public/`, and the lightbox row on `/gallery/general/`.
